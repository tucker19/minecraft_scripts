# Opt-in `chunk_dig_swarm` design

Swarm workers request small, exclusive patches from staging. One coordinator on the dashboard computer is the only allocator. Workers never use a peer's position, reported Y, or online status to choose a layer or infer that space is free.

The separate `chunk_dig_swarm.lua` and `swarm_coordinator.lua` are implemented and tested against simulated CC APIs. See [setup](README.md#opt-in-swarm-setup). The standalone worker, startup and checkpoint format are unchanged. The dashboard accepts optional swarm telemetry without changing the standalone packet format.

## Dynamic patch queue

- **Geometry:** Configure a quarry ID, dimension, world-coordinate footprint, clear approaches, and staging cells. The cell manifest is a whitelist: the allocator does not invent excavatable cells or transit through unknown space. Exclude output, fuel and modem fixtures from both work and paths. Keep unrelated standalone jobs outside the footprint and approaches.
- **Late joins:** Any registered turtle at a verified staging cell can request work. Search known clear cells for the shortest unreserved approach to unclaimed work. Grow a connected patch up to the configured cell and round-trip fuel limits. Reserve the patch and entire outbound/return route in one commit. Routes may be reused after release, but never shared by two active workers. Other staging cells are not transit. There is no chunk-based worker cap; concurrency is limited by reachable work, staging capacity and route conflicts. Workers wait at staging if no patch qualifies. Active patches are not split or preempted.
- **Onboarding:** Require fresh GPS at the designated staging cell, verified facing, the configured dimension and authenticated or trusted messages. A worker persists its grant before moving and validates the round trip before departure. The future runtime must refuse swarm startup if a standalone save exists; don't read, migrate, archive or resume it.

## Durable assignment protocol

Use directed messages on `turtle_quarry_swarm_v1`. Pin the coordinator computer ID; derive worker ownership from the message's sender, validate registration, and reject payload claims that disagree. Use bounded/versioned messages with `quarryId`, immutable `manifestId`, message type, and a persistent per-worker request sequence, plus `assignmentId` where applicable. Assignments bind the quarry, manifest, worker ID, never-reused assignment ID, partition, home and approach. A lost response is normal: [Rednet does not guarantee receipt and allows sender spoofing](https://tweaked.cc/module/rednet.html). The first release requires a trusted network; for an untrusted multiplayer deployment, authenticated messages and replay protection are prerequisites, not something IDs alone supply.

| Message | Coordinator/worker behavior |
| --- | --- |
| `REQUEST(seq, home)` | Worker commits its pending request before sending. Coordinator serializes requests in one event loop; validates eligibility, home, and sequence. Commit the owner, grant and replay result together before sending `GRANT` or a durable `WAIT`. A retry of the same sequence returns the same result; older or conflicting messages cannot allocate. A newer request from an assigned worker returns the existing assignment, never another. A worker retrying a `WAIT` for changed conditions uses a new sequence. |
| `GRANT(seq, assignment)` | Accept only from the pinned coordinator for the durable pending request and matching manifest. Commit the assignment and initial worker checkpoint together before actuation. A duplicate for the installed assignment may be acknowledged but must not reinitialize it. A mismatched grant freezes the worker if it conflicts with active state. |
| `SYNC(seq, assignmentId, generation)` | On reboot or reconnection, verify the exact durable grant, local checkpoint, manifest, and action journal before dispatching. A matching response confirms ownership, not position. A checkpoint without a grant, an unknown grant with evidence of prior execution, invalid state, or an ambiguous pose stops for diagnosis. A lost initial grant can be recovered only by replaying the still-pending bootstrap request, not by creating a replacement checkpoint for a turtle that may have moved. |
| `PROGRESS(assignmentId, evidenceSeq, evidence)` | Owner submits bounded, ordered, checkpoint-backed observations. Accept the next evidence sequence; replay success for identical duplicates, reject gaps or conflicts, and persist before acknowledgement. Keep unsent evidence in the worker checkpoint. Heartbeats update display freshness only; they never change ownership or clearance. |
| `FINISH(seq, assignmentId, evidence)` | After returning to the original staging cell, the worker durably disables the grant with no pending motion before requesting release. The coordinator checks sender, staging and checkpoint proof in the runtime adapter, then commits final cell observations and releases the route and patch together. Unreported cells stay unclaimed; blocked cells stay blocked. The worker retries the same finish until acknowledged and may then request another patch. Neither a reboot nor a heartbeat timeout releases anything. |

Place coordinator records in a separate directory on the dashboard computer, for example `/.chunk_dig_swarm_coordinator`, and worker records under `/.chunk_dig_swarm`. Include schema, immutable manifest, generation, assignment counter, request replay state and evidence cursor in the coordinator record. Use checked staged writes and alternating committed snapshots, following the standalone pattern but refusing to fall back to a record that might predate a published grant. A known interrupted staging write can be retried; missing committed state, generation inconsistencies, disk-full or an uncertain commit freeze allocation. Initialization is explicit; normal restart must not create a replacement ledger. Independent rollback of valid files may be undetectable: stop every worker and reconcile against real positions and saved IDs before using any restored coordinator. No second allocator or automatic failover.

Bind worker checkpoints and motion intents to the same immutable assignment and checkpoint generation. Reuse the journaled move/turn approach: drain the pre-existing turtle command queue before reconciling pose, resolve a pending move using matching GPS candidate positions, and stop for operator verification if facing is ambiguous. No test movement to guess heading. On a communication timeout stop new claims and excavation; an already-authorized worker may return only along its persisted private cleared route after local pose verification, fuel check, and fresh obstruction checks. At home it waits for matching coordinator confirmation. If it cannot verify a safe return, it stays put; an unload does not release the reservation. No chunk loader is required or added.

## Clearance, traversal, and fuel

- **Independent ledgers:** Track allocation (`unassigned`, `assigned`) separately from each cell's clearance (`unverified`, `blocked`, `verified_clear`). Put observations under the exact partition and world Y. A successfully occupied cell or an explicit post-dig air observation can certify clearance; a failed dig, protected ore, bedrock, turtle, unknown block, unreachable cell, or absent report cannot. Record reasons and keep unresolved cells visible. A layer is verified clear only if every expected cell has positive evidence; a strip summit, end-of-sweep event, or absence of a descent candidate is not proof. A stopped-at-bedrock or incomplete partition can be terminal without being all-clear.
- **Skip only the sweep:** Select the next unfinished work face from the partition's plan and keep unresolved cells in the ledger, even when deeper work is reachable; never choose Y from a peer. For a verified layer, replace sweep dispatch with a transit task only if there is a persisted contiguous route from private home (or the current verified pose with an intact home route) to the next work face and back. Require recorded clearance and reservations for every transit cell. A first assignment can mine its own unverified entry and work cells from an already safe staging cell; it cannot treat unverified cells as shortcut transit. For previously cleared layers, allow only guarded route traversal, no layer sweep and no blanket re-digging. If a route changes, invalidate affected clearance, stop or retreat via a verified alternate path, and replan; without one wait at home if already there, otherwise hold position. Never excavate a shortcut through another assignment.
- **Fuel:** At home require at least outbound path cost plus return cost plus work allowance and safety margin; on each work step include the cost of reaching home from the proposed next position, including retreats, shafts and detours. For unload/refuel, persist the exact return path and restore the work cursor and heading. No path, insufficient capacity, or unknown fuel means no departure. Revalidate reservations, path and reserve before entering another cell.
- **Action gate:** Authorize the world XYZ before any movement or dig (including detours, route repairs, isolated and underside digs, and all retry paths). Carry over the existing front/up/down turtle ID/tag guard before movement, immediately before every dig, and after a failed move before any fallback. On turtle detection report `waiting_turtle` with direction, hold all physical actions and route/checkpoint progress for 60 seconds, then inspect the same target. Repeat if necessary; after it clears, redispatch through authorization, fuel and the guard. Telemetry and non-mutating liveness messages can continue during the pause; process any state-changing messages later. As in standalone, separate inspect and dig calls are not atomic. The reservation is the primary defense against cooperative workers colliding; inspection is a second defense against unexpected obstacles.

## Integration and acceptance

`chunk_dig_swarm.lua` uses separate worker state and `swarm_coordinator.lua` runs explicitly on a dashboard computer. The implemented protocol commits local progress with the worker trail and sends final clearance on `FINISH`; intermediate `PROGRESS` streaming remains a design extension. The `turtle_quarry_v1` packet keeps ordinary telemetry and adds an optional `swarm` object with quarry ID, assignment ID, patch anchor and cell count, and waiting reason. The dashboard's offline timer is informational, not an allocation clock.

`swarm_patch_queue.lua` implements the scheduling core. `Queue.initial(config)` builds the explicit initial ledger from coordinate lists (`work`, `staging`, `clearApproach`); `Queue.open(snapshot, commit)` attaches the caller's synchronous durable writer to a validated saved ledger. The single-threaded adapter calls `claim(workerId, seq, staging, fuel)` and `finish(workerId, seq, staging, assignmentId, outcomes)`. The core does not verify GPS, worker checkpoints or block state itself. Only the runtime adapter may invoke a finish after verifying the owner's persistently disabled assignment and return to staging. The core freezes on an uncertain commit until reopened on verified state.

Run `python3 cctweaked/turtle/test_swarm_patch_queue.py` to exercise the Lua allocator with temporary-file commits. `python3 cctweaked/turtle/test_swarm_model.py` still covers the earlier fixed-area protocol model for boot and observation handshakes; it is not the dynamic queue. Neither test runs Rednet, GPS or turtle motion.

`python3 cctweaked/turtle/test_swarm_runtime.py` runs the real coordinator and worker in a shared world with simulated networking, GPS and filesystem APIs. It covers a late join, coordinator restart, interrupted translation, reboot without coordinator confirmation and 60-second pauses in all three directions. Further fault testing should cover independent rollbacks, storage exhaustion and long-lived deployment on a disposable in-game footprint. This is not live validation.
